# GiveTrack — Responsive NGO Website Development and AI Tool Comparison

**Lab Exercise 1: Responsive Web Page Layout**  
**Project:** GiveTrack — Donate • Track • Volunteer  
**Domain:** NGO management, donation transparency and volunteer matching  
**Repository:** `NGO-Website / GiveTrack-AI-Website-Comparison-Lab-1`

---

## 1. Introduction

GiveTrack is a responsive NGO website prototype designed around donation transparency and volunteer matching. It presents fundraising campaigns, donation records, expenditure information and volunteering opportunities through a dashboard-style interface.

The project was developed through a manual coding approach and four AI-assisted approaches: Antigravity, ChatGPT, Claude and Gemini. The same core website brief was used for the AI-generated versions. Their code and outputs were then inspected to identify differences in implementation, asset handling, page structure and functionality.

The project is a frontend demonstration using sample data. It is not connected to a production NGO database, a live payment gateway or a real audit system.

## 2. Objectives

The project objectives were to:

- Develop a professional, responsive NGO website.
- Present campaigns and fundraising progress.
- Show the relationship between donations, utilised funds and remaining funds.
- Display donation records and expenditure categories.
- Provide volunteer opportunities and a skill/availability matching feature.
- Apply modern frontend technologies and responsive layout techniques.
- Compare manually written code with websites generated by different AI tools.
- Inspect generated code, identify implementation gaps and refine the Antigravity version.

## 8. Code inspection and comparison of the AI-generated versions

The following observations come from inspecting the submitted HTML, CSS and JavaScript files and the folder contents. They are code-level findings, not claims that every interaction has passed a live browser test.

### 8.1 Gemini — single-file implementation

**Source reviewed:** `givetrack_platform.html`

Gemini returned the website as one standalone HTML file. The page markup, Tailwind configuration, custom CSS and JavaScript logic are contained in that file rather than being separated into dedicated HTML, CSS and JavaScript files.

**What the implementation includes**

- A dashboard-style layout with a welcome area and financial overview.
- Campaign cards with progress indicators.
- Donation transparency section with a Chart.js doughnut chart.
- Itemised expense entries.
- A recent donations table with a search filter.
- Volunteer opportunity cards.
- Skill and availability checkboxes that filter the displayed volunteer cards.
- A donation modal that updates sample donation totals, campaign progress, chart balance and the donation table in the current page session.
- Notification and toast interactions.

**Issues and limitations identified from the code**

1. **Supplied logo is not correctly integrated.** The header and footer image elements reference `image_dbcec3.jpg`. The supplied logo asset was not included under that filename in the reviewed standalone HTML delivery. The code falls back to a generated `placehold.co` GiveTrack text image when the image fails, so the provided illustrated GiveTrack logo is not reliably displayed.
2. **Single-file organisation.** CSS and JavaScript are embedded in the HTML. This makes the implementation less modular and does not follow the prompt's requested separation into HTML, CSS and JavaScript files.
3. **No volunteer application form.** The volunteer cards call `applyVolunteer()` and display a toast message. There is no separate volunteer application form for entering applicant details.
4. **Report downloads are demonstration messages.** The `downloadReport()` function displays a toast saying that a file is downloading; it does not generate or download the named PDF report.
5. **Volunteer matching behaviour is filter-based.** Selecting skill and availability checkboxes filters the opportunity cards. This is useful interaction, but it differs from a dedicated matching form with a separate results workflow.
6. **Navigation combines Donations and Expenses.** The main navigation uses a combined “Donations & Expenses” destination rather than separate navigation links for both sections, as requested in the common brief.
7. **External image dependency.** Campaign images are loaded from Unsplash URLs, and the page uses external CDNs for Tailwind, Chart.js, Lucide and Google Fonts. Some visual assets and styling therefore depend on internet access.

**Positive observations**

The page has a detailed, polished dashboard structure, clear financial presentation, campaign progress cards and multiple interactive elements. The donation demo updates several visible values rather than remaining a static button.

### 8.2 Claude — separated files, but logo path mismatch

**Source reviewed:** `index.html`, `styles.css`, `app.js` and `givetrack-logo.png`

Claude generated separate HTML, CSS and JavaScript files. The package also contains a `givetrack-logo.png` file.

**What the implementation includes**

- Responsive navigation and dashboard sections.
- Campaign cards and campaign progress information.
- Expense breakdown and Chart.js visualisation.
- Recent donation records.
- Volunteer opportunity cards.
- A Volunteer Matching Assistant with selectable skills and availability.
- A donation dialog with form inputs.
- CSV export functions for donation and expense records.

**Issues and limitations identified from the code**

1. **Logo asset path does not match the delivered folder structure.** The HTML references `assets/givetrack-logo.png` in both the header and footer, but the reviewed ZIP places `givetrack-logo.png` at the project root rather than inside an `assets` directory. As delivered, those relative paths do not point to the included file, which explains why the logo is not loaded in the website. The image is present in the package, but its path is incorrect.
2. **No separate volunteer application form.** The code contains a donation form and a Volunteer Matching Assistant, but no volunteer application form for submitting applicant details. Matching an opportunity and applying to volunteer are different actions.
3. **Report download scope is CSV-based.** The report functions generate CSV files for donation and expense information. The implementation does not provide the requested PDF audit report or 80G certificate documents.
4. **Matching is a recommendation feature, not an application workflow.** The matching logic calculates suitable opportunities from selected skills and availability, but the reviewed code does not provide a volunteer application submission form.
5. **The logo integration issue is a path/configuration problem.** The logo file itself is included; the HTML source path and actual file location need to be made consistent.

**Positive observations**

Claude's implementation is separated into HTML, CSS and JavaScript. It includes a skill/availability matching routine and actual CSV generation for donation and expense data. The page also includes a donation form and a chart-based expense view.

### 8.3 ChatGPT — organised multi-file implementation

**Source reviewed:** `GiveTrack/index.html`, `GiveTrack/style.css`, `GiveTrack/script.js`, `GiveTrack/givetrack-logo.png` and the generated `GiveTrack/README.md`

ChatGPT generated a structured project with separate HTML, CSS and JavaScript files, a logo asset and a project README. The generated README explains how to run the site locally, lists the main features and clarifies that demo donations are stored only in the current page session.

**What the implementation includes**

- A dashboard with a fixed sidebar navigation and a main content area.
- Campaign cards and a demonstration donation modal.
- Donation transparency chart and financial totals.
- Recent donation records with CSV export.
- A Volunteer Matching Assistant with a form for selecting skills and availability.
- Matching results based on the selected preferences.
- A donation form and session-only updates to the dashboard and campaign progress.
- Footer branding and social links.

**Issues and limitations identified from the code**

1. **Logo contrast against the theme.** The logo is placed directly in the dark teal sidebar, with no separate light background panel behind it. The darker parts of the supplied logo can visually merge with the sidebar colour, reducing the logo's clarity. The logo asset is referenced in both the sidebar and footer, but its presentation needs better contrast.
2. **Volunteer matching is not the same as volunteer application.** The matching form collects preferences and displays suitable opportunities. It does not provide a separate application form for a user to submit their name and contact details for a selected opportunity.
3. **CSV export is provided for donation records, not a full audit-document workflow.** The code includes donation CSV export, but does not implement downloadable audit PDFs or 80G certificates.
4. **The generated README describes the demo scope.** It correctly states that the demo donation updates are session-only, no payment is taken and no data is sent to a server. It is a run/features README rather than a comparative project report.
5. **Dashboard layout differs from the common navigation layout.** The implementation uses a fixed left sidebar rather than a conventional horizontal navigation bar. This is a design choice, but it is a structural difference from the common brief's header/navigation presentation.
6. **Logo visibility needs visual review at different sizes.** The same image path is used in the header/sidebar and footer, but the dark sidebar treatment makes the logo less distinct than it should be.

**Positive observations**

The code is organised into separate files and includes a dedicated README. The donation interaction updates the displayed figures and campaign progress within the current page session. The volunteer matching form produces results from selected skills and availability, and the donation table can be exported as CSV.

### 8.4 Antigravity — generated implementation and further refinement

**Source reviewed:** `Approach-2-Antigravity/index.html`, `Approach-2-Antigravity/style.css`, `Approach-2-Antigravity/script.js` and the supplied logo asset.

Antigravity generated a multi-file implementation with separate HTML, CSS and JavaScript files. The reviewed code includes sections for Home, Campaigns, Donations, Expenses, Volunteers and Reports. The JavaScript includes navigation handling, chart setup, donation modal logic, volunteer matching, volunteer application handling and report generation.

**Issues identified in the initial generated website**

1. **Incorrect navigation active-state behaviour:** the Donations tab remained highlighted when the user navigated to Expenses or Reports.
2. **Poor chart tooltip visibility:** the chart tooltip overlapped the chart and made numerical values difficult to read.
3. **Prefilled personal-looking information:** the volunteer application form contained prefilled name, email and phone details rather than neutral placeholders.
4. **Missing social media icons:** the footer showed empty circular elements instead of the expected social media icons.

These four issues were documented as part of the lab work.

#### Refinement process

Antigravity was the only AI-generated implementation for which a separate, focused refinement stage was documented as part of this lab exercise. After inspecting the generated website, a refinement prompt was supplied to correct the four observed issues while preserving the existing GiveTrack branding, colours, typography and overall layout.

The refinement prompt instructed Antigravity to:

- Correct the active navigation state for all sections, including Expenses and Reports.
- Reposition or reconfigure the chart tooltip so labels and numerical values remain readable.
- Remove prefilled personal details from the volunteer form and replace them with neutral placeholders while retaining validation.
- Restore the missing footer social icons with correct alignment and hover effects.
- Preserve the supplied logo and unrelated website sections.
- Retain responsive behaviour and check the updated code.

#### Changes reported by Antigravity

Antigravity reported that it:

- Reworked the page section structure and navigation active-state handling.
- Replaced the chart tooltip presentation with an external HTML tooltip.
- Removed prefilled form values and used placeholders.
- Added footer social icons using inline SVG elements.

This refinement stage demonstrates the use of a second, more specific prompt based on issues found during inspection of the initial output. The reported changes should be checked in the browser before they are described as fully verified.

**Positive observations**

The implementation is divided into separate HTML, CSS and JavaScript files. Its JavaScript includes dedicated functions for navigation, chart rendering, donation updates, volunteer matching, volunteer applications and report generation. It also includes a separate volunteer application flow, which is not present in the reviewed Gemini, Claude or ChatGPT versions.

## 11. Comparison of manual development and AI-assisted development

| Aspect | Manual implementation | AI-assisted implementation |
|---|---|---|
| Code creation | HTML, CSS and JavaScript are written and organised directly. | Code is generated from a natural-language prompt. |
| Initial design | Layout and components are assembled through direct coding decisions. | The tool interprets the design brief and produces its own layout and component structure. |
| Code organisation | The developer decides file separation and project structure. | Organisation varies by tool; in this project, Gemini returned one HTML file while the other AI versions used separate files. |
| Asset handling | The developer controls asset paths and placement. | The generated code may reference assets using paths that do not match the delivered folder structure, as seen in the Claude and Gemini versions. |
| Issue identification | The developer inspects and debugs the code directly. | Generated output must be inspected to identify missing features, path errors and interaction gaps. |
| Refinement | Code is edited directly. | Follow-up prompts can request targeted changes; the resulting code still requires review. |
| Verification | Browser testing is needed to confirm the page and interactions. | Browser testing is also needed; a tool's statement that it fixed an issue is not proof by itself. |

The comparison shows that AI tools can produce a substantial starting implementation, but their output differs in file organisation, logo integration and the completeness of requested workflows. Reviewing the actual code helps identify issues that may not be apparent from a screenshot alone.

## 12. Scope and limitations

- All versions are frontend demonstrations using sample information.
- No production database, real authentication, payment gateway or live NGO accounting integration is included.
- Donor names, transactions, campaign figures and contact details are demonstration content.
- A displayed “verified” label does not prove that a real independent audit has taken place.
- Demo donation interactions do not process actual payments.
- CSV export or a toast message should not be confused with a production reporting or audit system.
- Some versions use external CDNs, fonts or image services, so an internet connection may be required for all visual assets and libraries to load.
- The observations in the comparison are based on source-code inspection. Runtime behaviour and responsive layout should be confirmed in a browser before making claims about successful testing.

## 13. Conclusion

GiveTrack was developed using one manual approach and four AI-assisted tools. All versions were based on the same core website requirements, but the resulting implementations differed in code organisation, logo handling, volunteer workflows and reporting functionality.

The code inspection identified that Gemini returned a single-file implementation and did not correctly reference the supplied logo; Claude included the logo file but used a path that did not match its delivered location; and ChatGPT produced a well-organised multi-file project with a generated README, donation CSV export and a skill/availability matching form, although the logo presentation needs better contrast and the matching form is not a separate volunteer application form.

Antigravity was further refined as part of the lab exercise. Four issues were identified in its initial output, and a targeted refinement prompt was used to address navigation highlighting, chart tooltip visibility, prefilled volunteer form details and missing social icons.

The exercise demonstrates that a generated website should be evaluated by examining its source code and actual behaviour. Prompting is only one part of the process; checking asset paths, verifying interactions and refining identified issues are also necessary to produce a more complete frontend implementation.
